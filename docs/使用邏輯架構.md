# 使用邏輯架構

描述系統「怎麼運作」的規則層：角色權限、資料範圍、狀態流轉、關鍵業務邏輯。

## 一、角色與權限

| 角色 | 說明 | 資料範圍 |
|---|---|---|
| **Admin 管理員** | 系統管理者 | 全部據點、全部功能 |
| **Cadre 幹部** | 據點主管 | 所屬據點；可轉移、AI 入庫 |
| **SocialWorker 社工／據點人員** | 第一線 | 所屬據點；查詢、領用、捐贈、報廢、影像入庫 |

功能可用性（前端 `RoleGate` + 後端 Edge Function 雙重把關）：

| 功能 | Admin | Cadre | SocialWorker |
|---|:--:|:--:|:--:|
| 戰情總覽 / 物資清單 / 各紀錄查詢 | ✅ | ✅ | ✅ |
| 物資入庫 / 出庫 / 捐贈 / 報廢 | ✅ | ✅ | ✅ |
| 物資轉移 | ✅ | ✅ | ❌ |
| AI / 手機影像入庫 | ✅ | ✅ | ✅ |
| 系統管理（帳號/據點/庫存種類/LINE/AI 設定） | ✅ | ❌ | ❌ |

> 非管理員只能對「所屬據點」操作；沒有據點的帳號無法執行異動。

## 二、資料範圍（RLS）落實方式

- `supply_item` 等：`select` 限 `is_admin() OR location_id = my_location_id()`。
- 扣庫存寫入不開放 client 端；由 Edge Function 內先驗證 `role_name`、`location_id`，再以 `service_role` 寫入。
- 手機頁面一律以 `profile.location_id` 過濾（不分角色）；管理員若未指定據點則看全部。

## 三、物資的兩層資料模型

```
目錄（可選用的品項）                實際庫存（真的有的東西）
inventory_item_definition  ──┐
  (種類/名稱/單位/全域安全庫存) │
inventory_item_variant       │      supply_item（一個「批次」）
  (規格)                      └────→ 同一種類/名稱/規格 + 同效期 視為一批
location_inventory_safety_stock       有自己的數量、效期、據點、圖片
  (各據點門檻)
```

- 「入庫」是選目錄品項建立/加總 `supply_item` 批次。
- 「出庫/捐贈/報廢/轉移」是對既有 `supply_item` 批次加減量。
- **數量只能透過異動改變**（出/入/捐/廢/轉），物資清單的「編輯」用於修正效期/安全庫存/備註/圖片。

## 四、庫存狀態判定

| 狀態 | 條件 |
|---|---|
| 低庫存 | `quantity <= safety_stock` |
| 已過期 | `expiration_date < 今天` |
| 即將過期 | 今天 ≤ `expiration_date` ≤ 今天+30 天 |
| 正常 | 以上皆非 |

- 安全庫存警示：據點層級看 `location_inventory_safety_stock`，全系統層級看 `global_safety_stock`（皆只算門檻 > 0）。

## 五、轉移狀態機

`Pending`（建立即扣來源）→ `Confirmed`（目的地加量、合併同批次）或 `Cancelled`（退回來源，並還原被軟刪的來源列）。合併批次的判準：**種類 + 名稱 + 規格 + 效期**一致即同批（variant 連結僅在兩邊都有值且不同時才排除）。

## 六、AI 影像入庫原則

- 一律先進 `ai_stock_in_log`（待確認），**人工確認後**才寫正式庫存。
- 目錄比對：精確 → 同義詞（`catalog_synonym`）→ 目錄名稱 → 都沒有就當新品項。
- 確認後照片從 `ai-stockin` 搬進 `items` 集中管理。

## 七、LINE 通知邏輯

- **被動式**：只在異動成功後觸發，不背景輪詢。
- **去重複**：對目前警示清單算簽章，與上次相同就不重發。
- **對象**：只推給「已用綁定碼綁定且開啟通知」的帳號。

## 八、共通 UX 規則

- 建立/確認成功後 → 導回對應的清單/紀錄頁，並顯示成功訊息（`FlashMessage`）。
- 列表都有「篩選條件」卡（關鍵字＋維度下拉＋重設）。
- Edge Function 失敗時還原真正的中文錯誤訊息（`functionError`）。
